# REPO_STRUCTURE — как устроен репозиторий сейчас и какой должна быть целевая структура

**Дата:** 2026-10-22 · **Задача:** привести репозиторий в порядок так, чтобы его одинаково удобно было
читать и человеку, и LLM-агенту. Ничего не переименовано: всё, что ниже про «цель», — это план
с готовыми командами, а не сделанные изменения.

**Проблемы, которые видно по этой карте:**

1. **Два разных «README для ИИ»** — `AGENTS.md` (правила) и `agents/INDEX.md` (карта). Агент не знает,

2. **Данные, код и артефакты смешаны.** `dataset/` одновременно содержит исходники генераторов

3. **`research/`** содержит и заметки, и декомпиляцию, и скачанные ссылки — 181 файл смешанного смысла.
4. **Нет машиночитаемой карты для агента** в корне: `llms.txt` отсутствует.
5. **Мусор в корне:** `_shot.html` — отслеживаемый, но бессмысленный файл; `build/scratch/` (1.4 ГБ)
   в gitignore, но внутри — исходники C#-рантайма, которые стоит сохранить.

## 2. Целевая структура верхнего уровня

Предложение — **почти новое имя, почти новая раскладка, но без единого разрыва ссылок**.

```
CaptchaOCR/
├── AGENTS.md            # правила для агента: роли, контракт, команды, ловушки машины
├── llms.txt             # короткая карта для ИИ: что за проект, ключевые файлы, команды
├── README.md            # для человека: что за проект, как собрать, где смотреть результат
├── HANDOVER.md          # состояние проекта (что сделано, что дальше) — остаётся в корне
├── docs/                # НОВОЕ: человеческая документация, которой не место в reports/
│   ├── adr/             # решения с контекстом (почему так, а не иначе)
│   ├── glossary.md      # словарь: полоса, глиф, CTC, кадр, тип, группа A/B/C
│   ├── onboarding.md    # как поднять с нуля: java, venv, сборка, обучение
│   └── plan.md          # план работ, выведенный из HANDOVER §7
├── dataset/             # без изменений: генераторы + датасет живут вместе
│   ├── generator/       # Java-исходники 18 плагинов
│   ├── generator_ru/    # Java-исходники группы типов GalleryCaptcha
│   ├── out/  out_ru/    # сгенерированный датасет (в git)
│   └── real_shots/      # эталонные скриншоты (в git, но это НЕ обучающие данные)
├── train/  bench/  tools/   # без изменений: код обучения, харнессы, измерители
├── research/            # без переименования: находки и исходники апстримов
├── reports/             # измеренные результаты (никогда не править руками)
├── agents/              # документация для ИИ: INDEX, AGENT_LOG, DSH_HARNESS, REPO_STRUCTURE
└── .agents/skills/      # навыки харнесса (уже работают)
```

**Почему именно так:**

- **`docs/` вместо «всё в reports/».** Сейчас `reports/` — это и результаты измерений, и объяснения
  (например `PIPELINE_DESIGN.md` — это проектная записка, а не измерение). Для агента важно, что в
  `reports/` лежат **только измеренные числа**, и их нельзя править руками. Отчёт-проект и отчёт-измерение
  должны быть в разных местах.
- **`docs/adr/`** — потому что в проекте уже есть несколько решений, которые придётся объяснять
  заново каждому новому агенту: «почему полоса важнее модели» (измерено 0 % → 78 %), «почему 34 класса,
  а не 44», «почему датасет остаётся в git». Это ровно то, для чего нужны ADR.
- **`docs/glossary.md`** — у нас 46 типов, свой словарь (`roi`, `text` vs `answer`, группа A/B/C, `band`).
  Без глоссария агент тратит токены на выяснение терминов.
- **`dataset/` не трогаем.** Формат `dataset/out/<owner>/<repo>/<type>/` — это контракт, на который
  ссылаются `paths.py`, `build.ps1`, Java-генераторы, харнессы и `<atlas>/data/types.js`. Переименование
  даст ноль выигрыша и много поломок.
- **`research/` не переименовывать** — там лежат лицензионно-чувствие исходники апстримов; переезд
  ничего не улучшает, а историю git придётся переписывать.
- **Веса, кэши, чекпоинты** — остаются вне git (`.gitignore`), это уже сделано правильно.

## 3. Миграция: точный список `git mv` и что при этом ломается

**Предлагаемые переезды (выполнять отдельным коммитом, сразу после — править ссылки):**

```bash
# 1. Проектные записки и инструкции — из reports/ в docs/
git mv reports/PIPELINE_DESIGN.md      docs/pipeline-design.md
git mv reports/REVIEW_DATASET.md       docs/adr/0001-dataset-is-kept-in-git.md
git mv reports/REVIEW_MODEL_PLAN.md    docs/adr/0002-recogniser-architecture-and-data.md
git mv reports/REVIEW_RESEARCH.md      docs/adr/0003-plugin-identification-method.md

# 2. Сайт-атлас остаётся, но его данные — рядом с ним (уже так)
#    (<atlas>/data/types.js, <atlas>/data/meta.js — без изменений)

# 3. Личный файл в корне — прочь (не mv, а удаление):
git rm _shot.html
```

**Что сломается и где поправить после переездов** (проверено по коду, не по памяти):

| что | где искать | что поправить |
|---|---|---|
| путь `reports/PIPELINE_DESIGN.md` | `HANDOVER.md` §8 «Где что лежит», `agents/INDEX.md` §2, `reports/CAPTCHA_SYSTEM_OVERVIEW.md` | заменить на `docs/pipeline-design.md` |
| пути `reports/REVIEW_*.md` | `HANDOVER.md` §1.1, §6.5, `agents/INDEX.md` §2 | заменить на `docs/adr/...` |
| `reports/bench_results*.json` | **не трогаем** — это измеренные результаты, пути в `bench/*.py` остаются валидными | — |
| `dataset/out/...` | `paths.py`, `build.ps1`, `dataset/generator/dev/captcha/Gen.java`, `train/captcha_crnn.py` (`OUT_DIRS`), `bench/*.py`, `<atlas>/data/types.js` (`src_prefix`), `<atlas>/build_data.py` | **ничего не меняется** — датасет не переезжает |
| `<gallery-refs>/` | `<atlas>/build_data.py`, `tools/*.py` | не меняется (референсы остаются в каталоге референсов) |
| новый `llms.txt` | — | только новый файл, ссылки в нём указывают на существующие пути |

**Порядок:** (1) `git rm _shot.html`; (2) создать `docs/` и `docs/adr/`; (3) `git mv` записки; (4) разом
поправить ссылки в `HANDOVER.md`, `agents/INDEX.md`, `reports/CAPTCHA_SYSTEM_OVERVIEW.md`; (5) добавить
`llms.txt`; (6) обновить `agents/INDEX.md` (карта репозитория) — он для того и нужен, чтобы такие
переезды делались по списку, а не на глаз.

**Проверка после миграции:** `git ls-files` не должен измениться по количеству (6831 − 1 за `_shot.html`);
`python tools\check_labels_and_roi.py dataset\out_ru` — без ошибок; `javac` обоих генераторов — чисто.

## 4. Что не трогаем и почему

| объект | решение | обоснование |
|---|---|---|
| `dataset/out/`, `dataset/out_ru/`, `real_shots/` | остаются в git | без датасета модель не обучаема; 79 МБ — приемлемо, клонирование быстрое |
| `<gallery-refs>/` (525 референсов) | остаются в git | это единственные настоящие скриншоты группы типов GalleryCaptcha; **но это референсы, а не обучающие данные**, и их нельзя использовать для обучения без проверки правил GalleryCaptcha (см. `reports/research2/H_v1_family.md`) |
| `research/` | не переименовывать | там лицензионно-чувствие исходники; переезд не даёт выигрыша |
| `build/scratch/` (1.4 ГБ, вне git) | **не удалять вслепую** | внутри — исходники C#-рантайма и релиз ORT (по отчёту T2). Их стоит сначала перенести в `research/runtime/` или `bench/runtime/`, и только потом чистить |
| `build/hf_cache` (4.16 ГБ) | удалён | кэш скачанных весов, восстанавливается одной командой |
| `pip-*`, `torchinductor_Title`, корневой `__pycache__` | удалены | пустые каталоги от pip и torch, ничего не содержат |
| `train/run/` (1 ГБ чекпоинтов) | остаётся вне git | артефакты прогонов, воспроизводимы |
| `.venv-gpu/` (4.6 ГБ) | остаётся вне git | переустанавливается одной командой из `train/README.md` |

**Ещё два мусорных места, которые стоит закрыть:**
- `_shot.html` в корне — **отслеживаемый** мусор (снимок экрана, попал в коммит). Удалить через
  `git rm _shot.html` — в рамках ограничения «ничего не удалять» это предложение, а не действие.
- `build/scratch/` — 1.4 ГБ черновиков: `roi_fix2_out/`, `full_v2/`, `lr_0.001/` и десятки подобных папок с
  копиями датасета и чекпоинтов. Их можно удалять хоть каждый день, но сначала — вынести из
  `scratch/` то, что имеет ценность.

## 5. Практики, которые стоит взять (источники)

1. **`llms.txt`** — предложение Джереми Хоуарда (Answer.AI), v2 от 10.08.2026: markdown-файл в корне
   с H1, кратким описанием в блокquote и разделами со ссылками на детальные документы; агент читает
   карту и сам докачивает нужное. Формат: H1 (единственный обязательный раздел) → блокquote-описание →
   разделы H2 со списками `- [название](путь): пояснение`; раздел «Optional» — для второстепенного.
   <https://llmstxt.org/> · <https://github.com/AnswerDotAI/llms-txt>
   **У нас:** у репозитория 9 отчётов, 4 документа для ИИ и 5 скриптовых подсистем — карта из 20 строк
   сэкономит агенту десятки тысяч токенов на каждом холодном старте.
2. **`AGENTS.md` как стандарт** — открытый формат, используется в 60k+ репозиториев, поддерживается
   Codex, Cursor, Aider, Gemini CLI, Copilot, Zed, Warp и другими; ведётся под Linux Foundation
   (Agentic AI Foundation). Ключевое правило: **ближайший к изменяемому файлу `AGENTS.md` выигрывает**,
   а явные указания в чате — важнее всего. Формат: обычный markdown, обязательных полей нет.
   <https://agents.md/> · <https://github.com/agentsmd/agents.md> · <https://agentsstandard.com/>
   **У нас:** `AGENTS.md` уже есть и работает (его читает DeepSeek Harness — проверено в
   `agents/DSH_HARNESS.md`); стоит лишь добавить вложенные `AGENTS.md` в `dataset/generator/` и `train/`
   с доменными правилами (как в примере из `openai/codex`, где их 88 на монорепозиторий).
3. **`docs/adr/`** — записи решений с контекстом. У нас как минимум три решения, которые неочевидны и
   требуют объяснения: «датасет остаётся в git», «полоса важнее модели», «свой CRNN против готовой
   PP-OCRv6». Каждое — с «почему», «альтернативы», «последствия».
4. **Глоссарий** — у проекта 46 типов и собственные термины (`text` vs `answer`, `roi`/полоса, группа A/B/C,
   `band`, `faithful`/`clean-room`/`reconstructed`). Термины разъезжаются между отчётами; глоссарий их
   фиксирует.
5. **Разделение данных и артефактов** — крупные бинарники (веса, чекпоинты, кэши) держать вне git, а
   исходники и измерения — внутри; лёгкий клон быстрее и не раздувает диффы. У нас это уже сделано
   (`.gitignore`), и это стоит **зафиксировать в правилах**, чтобы новый агент не начал коммитить веса.

## 6. Что делать дальше (по порядку)

1. `git rm _shot.html` — одна строка, чисто.
2. Создать `llms.txt` в корне (карта для агента) и `docs/glossary.md` — по 20–30 минут.
3. Завести `docs/adr/` и перенести туда три отчёта-решения с обновлением ссылок.
4. Вынести ценное из `build/scratch/` (исходники C#-рантайма) в `research/runtime/`, остальное удалить.
5. Обновить `agents/INDEX.md` под новую раскладку.

**Отдельно отмечу, чего я не делал:** ничего не переименовывал и не перемещал, `.gitignore` поправил
только на непокрытые пути (`pip-*`, `torchinductor_*`, `*.raw`; `<gallery-refs>/**` в игнор **не добавлял**,
потому что эти 525 файлов уже отслеживаются и игнор просто не сработал бы), коммит не делал.

## 7. Фаза 2: минимализм по итогам исследования (2026-10-22)

Исследование — `agents/REPO_CONVENTIONS_RESEARCH.md` (15+ поисков, 6 первоисточников: llmstxt.org,
agents.md, agentsstandard.com, arXiv:2602.11988 — исследование ETH Zurich AGENTbench, Anthropic про
context engineering, repomix). Главный вывод источника: **контекст-файлы могут вредить** —
LLM-автогенерированные снижают успех на 3 %, написанные человеком дают +4 % при +19 % стоимости, а
обзоры архитектуры не помогают вовсе; вред приходит от **дублирования** того, что агент прочтёт сам.
Отсюда — решения ниже.

| что | было | стало | почему |
|---|---|---|---|
| `AGENTS.md` (всегда-on) | 25 899 Б | **18 628 Б** | карта каталогов, «текущее состояние» и инструкция «как добавить тип» вынесены в `agents/INDEX.md`, `HANDOVER.md` и `dataset/generator/AGENTS.md`; добавлена строка про бюджет контекста (64 КиБ у харнесса, 32 КиБ у Codex) и про headless-браузер |
| `research/runtime/` | 53 файла, 33.8 МБ | **2 файла, 10 КБ** | 46 одноразовых проб-скриптов удалены; сборки (`onnxruntime.dll` 16.5 МБ, `exe`, `.obj`, `.onnx`) выкинуты — это артефакты, не исходники; остались `csharp/Program.cs` и `native/config.json` + новый `README.md` о пересборке |
| `research/briefs/` | 15 файлов | **удалён** | это одноразовые входные ТЗ для агентов-исследователей; результат исследования — в `reports/research2/` (10 отчётов), а не во входах |
| `research/__pycache__/` | 3 файла | удалён | кэш |
| `CONTINUE.md` | 10.5 КБ, «краткий промпт» | **14 КБ, самодостаточный** | новая сессия должна понять состояние, прочитав только его: что за проект, все измеренные числа, что не сделано, план по приоритету, открытые решения владельца, ловушки машины |
| `llms.txt` | 5.5 КБ | обновлён | новые пути (`docs/`, `agents/REPO_CONVENTIONS_RESEARCH.md`), 10 отчётов в `research2/`, ссылка на `docs/pipeline-design.md` |

**Что НЕ сделано намеренно (по вердиктам исследования):** `CLAUDE.md`, `.cursorrules`, `.clinerules`,
