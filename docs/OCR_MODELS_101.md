# Глава 1. Что такое OCR

## 1.1. Задача словами

**OCR** (Optical Character Recognition) — «оптическое распознавание символов»: дать программе
картинку с текстом и получить из неё **строку символов**. Это ровно то, что нужно капче: картинка →
«6aFij» → игрок вводит «6aFij».

«Модель» здесь — просто **числа**: подобранные веса нейросети, которые реализуют функцию
«картинка → распределение вероятностей по символам». Модель = архитектура (как устроена сеть) +
обученные веса (числа) + словарь (какие символы она вообще умеет произносить). Готовую модель можно
скачать и сразу использовать; дообучение = продолжить подстраивать эти числа на своих данных.

## 1.2. Задача на самом деле распадается на пять разных подзадач

Их часто путают, а они требуют разных моделей:

| Подзадача | Вопрос на входе | Ответ на выходе | Типичный пример |
|---|---|---|---|
| **Detection (детекция)** | «Где в этой картинке текст?» | прямоугольники/полигоны вокруг строк | DBNet, CRAFT ([arXiv:1904.01941](https://arxiv.org/abs/1904.01941)) |
| **Recognition (распознавание)** | «Что написано в этой строке?» | строка символов | CRNN, PP-OCR, TrOCR — **наша задача** |
| **Spotting (споттинг)** | «Где и что написано?» | строки **вместе** с их координатами | связка детектора + распознавателя |
| **Classification (классификация)** | «Это цифра или буква? Какой это цвет?» | один класс из списка | «это красный?» → `Red` |
| **Document parsing (разбор документа)** | «Что и как на этой странице?» | Markdown/HTML с таблицами, формулами, порядком чтения | MinerU2.5, PaddleOCR-VL, dots.ocr |

> **Важно для проекта.** 15 типов из 46 у нас — это **не** распознавание, а классификация или
> «текста в кадре нет вовсе» (ответ-цвет, ответ-номер слота, константный ответ). Ещё 9 типов —
> распознавание **плюс** шаг solver'а. Подробная разбивка: `agents/INDEX.md` §4, сводка — в
> `reports/research3/DATASET_AUDIT.md` §2.

## 1.3. Что такое VLM (коротко; подробно — глава 3)

**VLM** (Vision-Language Model, визуально-языковая модель) — это **языковая модель, которая умеет
смотреть**. Вместо того чтобы «классифицировать пиксели», она принимает картинку и **генерирует текст
токен за токеном**, как ChatGPT, но с картинкой на входе. Примеры: Qwen-VL, PaddleOCR-VL, GOT-OCR2,
Florence-2, DeepSeek-OCR.

Главное отличие от OCR-движка: OCR-движок — это **одна узкая функция** («строка → строка»),
а VLM — **универсальный собеседник с картинкой**. Отсюда и плюсы (понимает формулы, таблицы, язык),
и минусы (генерирует лишнее, «галлюцинирует», медленный, дорогой по памяти).

## 1.4. Наш конвейер: полоса и solver

Капча в Minecraft-плагине — это **не всегда картинка с кодом**. Это **сцена**: чат, окно инвентаря,
панель, композит-галерея, где ответ — одна строка среди многих. Отсюда два шага, которых нет в
«наивном OCR»:

1. **Полоса `roi` (cropper).** В `labels.jsonl` у 29 типов из 46 есть прямоугольник `[x, y, w, h]` —
   полоса с ответом. Плагин на инференсе известен, значит положение полосы известно **заранее** и
   учить его не надо. У 17 типов `roi = null` — там весь кадр и есть текст.
   *Правило проекта: полоса, которая не помещается в кадр, — это не полоса (`roi = null`).*

2. **Шаг solver'а.** В 9 типах из 46 то, что **нарисовано** (`text`), отличается от того, что
   **вводит игрок** (`answer`): развернуть строку, посчитать выражение `19 - 11`, перевести русские
   слова-числа в цифры. Распознаватель читает `text`; преобразование делает код.

**Как это выглядит в одном блоке:**

```
известен плагин
  → per-type конфиг { roi, маска charset, приоритет длины, пост-обработка }
  → кроп по roi → масштаб до нужной высоты глифа → нормализация
  → РАСПОЗНАВАТЕЛЬ (CNN + CTC) → распределение по символам
  → CTC-декод с маской по типу → пост-обработка (reverse / вычислить / слова→цифры)
  → ответ
```

Подробное описание шага «картинка → тензор» (с реальными примерами и числами) — в
[`docs/INPUT_PIPELINE.md`](INPUT_PIPELINE.md); краткая версия — в главе 6.

## 1.5. Словарик аббревиатур (каждую — один раз)

| Сокращение | Что это | Одна строка |
|---|---|---|
| **OCR** | Optical Character Recognition | картинка → текст |
| **VLM** | Vision-Language Model | языковая модель, которая умеет смотреть на картинку и говорить текстом |
| **CRNN** | Convolutional Recurrent Neural Network | свёрточная сеть + рекуррентная сеть, читающая строку слева направо ([arXiv:1507.05717](https://arxiv.org/abs/1507.05717)) |
| **CTC** | Connectionist Temporal Classification | способ учить распознаватель строки **без** выравнивания «символ ↔ позиция» ([arXiv:1507.05717](https://arxiv.org/abs/1507.05717)) |
| **Transformer** | архитектура с attention | сеть, которая сама решает, на какие части изображения смотреть ([arXiv:1706.03762](https://arxiv.org/abs/1706.03762)) |
| **LNN / LTC** | Liquid Neural Network / Liquid Time-Constant | сеть с **непрерывным временем**: состояние «течёт» по уравнению дифференциации ([arXiv:2006.04439](https://arxiv.org/abs/2006.04439)) |
| **STR** | Scene Text Recognition | распознавание текста в сценах (наша подзадача Recognition) |
| **DET / REC** | Detection / Recognition | найти строку / прочитать строку |
| **CER** | Character Error Rate | «сколько символов испорчено» (0 = идеально, 1 = всё неверно) |
| **exact match** | — | метрика «строка совпала целиком»; у нас — главная |
| **W-Avg** | Weighted Average | средняя точность с весами по объёму данных в бенчмарке |

# Глава 3. Что такое VLM

## 3.1. Определение и как оно устроено

VLM = **языковая модель + зрение**. Устройство: визуальный энкодер превращает картинку в «токены
изображения», а затем обычный языковой декодер (по типу GPT) **генерирует текст** по этим токенам.
Примеры наших интересов: `Qwen3-VL`, `PaddleOCR-VL`, `MinerU2.5`, `dots.ocr`, `GOT-OCR2.0`,
`Florence-2`, `SmolDocling`, `DeepSeek-OCR`.

Ключевое свойство: выход — **свободный текст**, а не фиксированная строка из словаря. Отсюда всё
плюсы и всё минусы.

## 3.2. VLM против OCR-движка

| | OCR-движок (CRNN, PP-OCR, SVTR) | VLM |
|---|---|---|
| Что выдаёт | строка из фиксированного словаря | свободный текст |
| Сколько стоит | 5–20 М параметров, десятки мс | 0.25–4 Б параметров, сотни мс–секунды |
| Что умеет | «строка → строка» | документ → Markdown, формулы, таблицы, язык, рассуждение |
| Как ломается | тихо: не тот символ | шумно: дорисует лишнее («галлюцинация»), напишет пояснение |
| Метрика | exact match по строке — честная и строгая | «примерно правильно» — метрику приходится придумывать |

## 3.3. Почему для капчи это дорого и обычно хуже — по нашим же цифрам

1. **Дорого по железу.** `PP-OCRv6_medium_rec` в нашем замере: **2.34 ГБ VRAM и 101 img/s** при
   обучении (`reports/research3/MODEL_LANDSCAPE.md` §6.3), 25.9 мс на картинку в ONNX-CPU
   (`reports/bench_models/ppocrv6-medium.json`). У `anuashok/ocr-captcha-v3` (TrOCR-архитектура) —
   **110.9 мс** на ту же картинку, вчетверо медленнее. VLM-ы в этом ряду стоят ещё на порядок выше:
   0.9–4 Б параметров, генеративное декодирование токен за токеном.
2. **Не наша задача.** VLM-OCR обучен на **документах**: страницы, колонки, таблицы, формулы.
   Наша картинка — это 3–8 символов, часто в шумной сцене. Предобучение VLM здесь не помогает, а
   мешает: модель «хочет» выдать осмысленную фразу и выдумывает её.
3. **Окно обучения не закрывается.** Дообчать 0.9–4 Б на 11.8 ГБ можно только через LoRA, а это
   1–4 img/s и 10–15 эпох максимум — капче нужно больше.
4. **Метрика размывается.** Exact match по строке — простая и честная метрика. Для VLM пришлось бы
   придумывать «насколько ответ близок к ожидаемому», и сравнение моделей становится шумным.

> **Честная оговорка.** У VLM есть **одна** реальная польза для нас: арифметические типы
> (`19 - 11`) и русские слова-числа — это язык и математика, а не «прочитать глиф». Но эти 9 типов
> из 46 решаются **детерминированным кодом** (калькулятор + лексикон на 40 строк), который мы и так
> пишем. Покупать ради этого гигабайт весов не нужно.

# Глава 4. Liquid / continuous-time

*(коротко и окончательно — вы просили «вспомнить, что это»)*

## 4.1. Что это

**Liquid Neural Networks** — семейство нейросетей, где **время входит в уравнение состояния**.
Обычная RNN обновляет состояние дискретно: `h[t+1] = f(h[t], x[t])`. «Жидкая» сеть вместо этого
описывает **непрерывную динамику**: `dh/dt = f(h, x(t), t)`, а выход — это значение этой системы в
нужный момент. Ключевая идея — **переменная постоянная времени**: у каждого «нейрона» своя скорость
реакции, и она зависит от входа.

Два базовых представителя:

- **LTC** (Liquid Time-Constant Networks) — обучаемая ODE-система с нелинейными воротами,
  [arXiv:2006.04439](https://arxiv.org/abs/2006.04439) (2020). Свойства: устойчивость, ограниченное
  поведение, выигрыш на временных рядах.
- **CFC** (Closed-form Continuous-time) — то же самое, но **без численного решателя ОДУ**: решение
  получается в замкнутом виде, [arXiv:2106.13898](https://arxiv.org/abs/2106.13898) (2021). Именно CFC
  сделали практичным: «ODE-нейросеть без решателя» — это быстро.
- **LFM** (Liquid Foundation Models) — коммерческая линия Liquid AI: LFM2 (июль 2025,
  <https://www.liquid.ai/blog/liquid-foundation-models-v2-our-second-series-of-generative-ai-models>),
  LFM2.5 и LFM2.5-VL (<https://www.liquid.ai/models>, <https://huggingface.co/LiquidAI/LFM2.5-VL-450M>).

## 4.2. Зачем это придумали

1. **Событийность.** Сеть «спит», пока событий нет, и реагирует, когда они случаются. Это важно для
   датчиков, робототехники, носимых устройств.
2. **Непрерывное время.** Нет фиксированного шага дискретизации: «между кадрами» сеть эволюционирует
   сама.
3. **Крошечные размеры.** Несколько сотен тысяч параметров вместо миллиардов.
4. **Быстрый инференс на CPU/NPU** — отсюда и маркетинг «edge AI».

## 4.3. Честный вердикт для нашей задачи — **красный**

| Вопрос | Ответ |
|---|---|
| Есть ли готовые OCR-модели на LTC/CFC? | **Нет.** Ни на Hugging Face, ни в виде чекпоинтов для OCR я их не нашёл. Есть исследования «LNN + CTC» в вузовских статьях, но это не публикуемые веса и не бенчмарки. |
| Что мы выиграем? | Ничего измеримого: наш вход — **статичная картинка**, а не поток событий. Непрерывное время здесь не даёт преимущества: у капчи нет временной оси, которую надо моделировать. |
| А размер? | Да, LNN действительно маленькие. Но маленькая модель на 23 000 синтетических картинках **выучит 46 стилей и забудет всё остальное** — это мы уже измерили на нашей CRNN (100 % на обученных типах против 37.20 % на удержанных). |
| А latency? | Узкое место у нас — **не модель, а кроппер и вход** (глава 5). Экономить 10 мс на распознавателе при потере 30 % точности — обмен, который нам не нужен. |

**Вывод:** «жидкие» сети — это **интересная и правильная идея в другой задаче** (потоковые сенсоры,
edge-агенты), а не кандидат для капчи. В таблицу главы 2 они внесены с честным «🔴» и без
приукрашивания. Если владельцу хочется «потыкать современные идеи» — это отдельная, короткая
экспериментальная ветка (собрать CTC-голову поверх LTC-энкодера и **сравнить на 10 типах**), но
**не публикуемая модель и не основной план**.

# Глава 5. Рекомендация

## 5.1. Одно направление, которое мы выбираем

> ### `CaptchaOCR-v1` = `PP-OCRv6_medium_rec`, дообученный на нашем домене **и смешанный с исходными весами** (WiSE-FT, β ≈ 0.4), с per-plugin входом по полосе `roi`, опубликованный на Hugging Face.

Почему именно это:

1. **Это единственная готовая модель, которая на наших данных уже работает** (0.4043 по всем типам,
   0.5517 по полосам; 58.80 % медианы на 7 удержанных типах). Мы не начинаем с нуля — мы дорабатываем
   то, что уже умеет.
2. **Она влезает в наш железный конь и по памяти, и по скорости:** 19.1 М параметров, 2.34 ГБ VRAM
   при batch 16, **101–119 img/s** при обучении на GTX 1080 Ti (измерено). Полный прогон по 13 типам
   (6 499 картинок, 20 эпох) занял **36.4 минуты**.
3. **Лицензия Apache-2.0** — публикуем на HF без юридических заморочек (в отличие от base TrOCR,
   где лицензия в карточке не объявлена, и доменных CRNN с MIT-атрибуцией).
4. **Нативный PyTorch-путь в `transformers 5.19`** (`PPOCRV6SmallRecForTextRecognition`) — без
   paddlepaddle, который под Windows + Python 3.14 не ставится.
5. **Мы уже нашли рецепт, который выигрывает, и он измерен.** Голое дообучение **проигрывает**
   предобучению (58.80 % → 48.00 % медианы). Но **подмешивание весов** — WiSE-FT,
   `Θ(β) = β·Θ_дообуч + (1−β)·Θ_предобуч`, при **β = 0.4** — даёт **63.80 %** медианы и 61.23 %
   micro: **+5.00 п.п. к базовой линии**, и при этом ни на одном из 7 типов не теряет.
   Это ровно тот приём, который нужен: дообучение добавляет доменное знание, а смешивание
   сохраняет универсальность предобучения. **Именно эта смесь опубликована на HF** (коммит
   `43a65582…`, 8 файлов, 77 085 348 Б).

**Честная оговорка, которую надо написать в карточке модели.** Коэффициент β = 0.4 и номер эпохи
(7) выбирались **на том же удержанном наборе**, на котором потом измеряли результат. Значит
63.80 % — **оптимистичная** оценка: она включает эффект подбора гиперпараметра. Честная независимая
проверка (β, выбранный на одном фолде, измеренный на другом) — **не сделана**, и это первая задача
из плана ниже.

**Почему не «просто дообучить сильнее»:** мы уже это делали дважды, с LR 1e-4 (13 типов / 1 299
картинок) и с LR 1e-5 (13 типов / 6 499 картинок, 20 эпох) — оба раза held-out просел. Причина одна и
та же: модель **специализируется** на обучающих стилях. Смешивание весов — это не «ещё немного
обучения», это **другая операция**: она берёт знание из обеих точек.

## 5.2. План на эту неделю — 6 шагов

| # | Шаг | Что делаем | Как измеряем успех |
|---|---|---|---|
| **1** | **Независимая проверка α (β)** | Сейчас β = 0.4 и эпоха выбраны на том же held-out, где измерялись. Пересчитать β на **одном** фолде и измерить на **другом** (или на полном 4-фолдном сплите) — это единственный способ узнать честное число | Медиана по held-out типам **≥ 58.80 %** (нулевой шаг) на **независимом** фолде. Сейчас максимум 63.80 % на том фолде, где β подбирали |
| **2** | **Кроппер и вход — приоритет № 1** | Для каждого типа: проверить, что полоса покрывает весь ink ответа (цветовое правило), привести глиф к 48 px (высота, которую ждёт PP-OCRv6), снять «по полосе» vs «по кадру». Отдельно разобрать провальные типы: `laforetbrut/are-you-sure/code` даёт **0.00 %** не потому, что модель плохая, а потому что **полоса низкоконтрастная и с мусорными точками** (измерено: у 499 из 500 предсказаний неверная длина) | Разрыв «полоса/кадр» по типам; рост медианы на 29 типах с полосой. Метрика: exact match по полосе и по кадру |
| **3** | **Починить словарь и charset** | В `PP-OCRv6_medium_rec` **нет кириллицы** (измерено: ни одна запись `character_list` не содержит кодовой точки U+0400–U+04FF) ⇒ 5 кириллических типов выпадают из обучения. Плюс в наших метках есть пробел, `+ - * '`, которых нет в charset тренера | Число типов, реально доезжающих до обучения (сейчас цель — ≥ 21 тип вместо 13). Кириллию — либо отдельной базой `cyrillic_PP-OCRv5_mobile_rec` (наш замер 0.3217), либо расширением головы на 33 класса |
| **4** | **Данные: догоняем 23 000 → все 46 типов** | Сейчас в обучение доезжают 13 типов / 6 499 картинок из 46 / 23 000. Остальные отсекаются фильтрами (нет полосы, кириллица, группа C). Первое, что нужно: понять, **какие типы ещё можно вернуть в обучение** (правка charset + расширенный словарь + `--allow-no-roi` там, где весь кадр = текст) | Доля доступных данных: сейчас ≈ 28 % от 23 000, цель — ≥ 60 % |
| **5** | **Решить судьбу второй модели** | Наша CRNN+CTC с нуля (100 % на обученных типах, 37.20 % на удержанных) — либо честно закрыть её как «дешёвый baseline, не публикуем», либо оставить как **модель B для кириллицы** (свой charset) | Решение зафиксировано в отчёте; не тянем две модели без нужды |
| **6** | **Дописать карточку модели и добить публикацию по лицензиям** | Модель и датасет **уже на HF** (`Titlehhhh/captchaocr-ppocrv6`, коммит `43a65582…`; `Titlehhhh/captchaocr-dataset`, коммит `6248c5b9…`). Осталось: (а) вписать в карточку честное предупреждение, что β выбран на том же held-out; (б) сделать **per-family репозитории** — лицензии плагинов разные (GPL-3.0 / AGPL-3.0 / нет лицензии), монолит выкладывать нельзя; (в) дописать инструкцию по загрузке и пример `from_pretrained` | Человек с другой машины делает `from_pretrained(...)`, получает наши числа; карточка не содержит неправды про метрики |

**Порядок важен:** шаг 2 (кроппер) даёт больше, чем шаг 1 (дообучение). Сначала чиним то, что
измерено как главный bottleneck. Шаг 4 (данные) — самый большой рычаг в перспективе, но он дольше
всех остальных.

## 5.3. Что мы НЕ делаем и почему

| Не делаем | Почему (одна строка) |
|---|---|
| **Не покупаем VLM-OCR** (PaddleOCR-VL, MinerU2.5, dots.ocr, DeepSeek-OCR, GOT-OCR2, Florence-2, SmolDocling, Qwen-VL) | 0.25–4 Б параметров, обучение в 11.8 ГБ не влезает, задача «страница → разметка», а у нас 5 символов; метрика exact match для них шумная |
| **Не строим распознаватель на диффузии** (DODO, MinerU-Diffusion) | Диффузия выигрывает на параллельном декодировании длинных страниц; у нас вывод из 5 токенов, выигрыша нет, а сложность и цена максимальны |
| **Не делаем Liquid / continuous-time распознаватель** | Нет готовых OCR-весов, нет метрик на капчах, задача не про события; максимум — короткий эксперимент на 10 типах, не публикуемая модель |
| **Не возрождаем «свою CRNN с нуля» как финальную модель** | Измерено: 100 % на обученных типах, 37.20 % медиана на удержанных — модель запоминает; PP-OCRv6 на тех же данных даёт 58.80 %, а с WiSE-FT 63.80 % |
| **Не дообучаем PP-OCRv6 «в лоб» и не публикуем голый fine-tune** | Измерено дважды: голый fine-tune **проигрывает** предобучению (58.80 % → 48.00 % медианы, при LR 1e-4 было 0.60 → 0.41). Публиковать надо **смесь** (WiSE-FT β ≈ 0.4 → 63.80 %) |
| **Не берём TrOCR / PARSeq как основу** | Измерено на наших данных: `trocr-small-printed` после дообучения — **0.20 %** медианы против 58.80 % у PP-OCRv6, и **в 5 раз медленнее**; PARSeq нет в `transformers` и требует отдельного фреймворка |
| **Не публикуем один монолитный датасет/модель «всё сразу»** | Лицензии плагинов разные (GPL-3.0 / AGPL-3.0 / нет лицензии) — нужны репозитории по семействам (`HANDOVER.md` §7) |
| **Не учим на типах без полосы «как на кадре» бездумно** | Тип без полосы (`roi = null`) — либо «весь кадр = текст» (осознанно, флаг `--allow-no-roi`), либо не OCR-задача вовсе |
| **Не публикуем `real_shots/`** | Это чужие скриншоты; в публичный датасет и на HF они не идут (`AGENTS.md` §8) |

# Глава 6. Как картинка попадает в модель

*(короткая версия; полная — в [`docs/INPUT_PIPELINE.md`](INPUT_PIPELINE.md))*

**1. Что лежит на диске.** 46 типов, в каждом 500 PNG + `labels.jsonl` (одна строка JSON на картинку:
`file`, `plugin`, `captcha`, `answer`, `text`, `prompt`, `roi`, `width`, `height`, `source`). Именно
`roi` — та самая полоса, про которую вся глава 5: у 29 типов она есть, у 17 — `null`. Правило
проекта: **полоса, которая не помещается в кадр, — это не полоса**.

**2. Кроп.** Известен плагин → известен `roi` → вырезаем прямоугольник, зажимая его в границы кадра.
Это **константа per-plugin**, её не нужно учить. Для типов без полосы берём весь кадр.

**3. Масштаб и нормализация.** Дальше картинка приводится к тому, что ждёт сеть: PP-OCRv6 принимает
**3 канала, высоту 48 px, ширину до 320** (ширина по аспекту, добивка нулями справа), BGR-порядок,
нормализация `(x/255 − 0.5) / 0.5`; наш CRNN — 1 канал и высоту **глифа** 32 px. Важная деталь:
масштабируем по **высоте глифа**, а не по высоте полосы (в полосе с русскими словами глиф — примерно
1/5 полосы), иначе 8-пиксельный текст в 128-пиксельном кадре превращается в нечитаемую кашу.

**4. В сеть и из сети.** Наша CRNN: 4 свёрточных слоя (32→64→128→256), три пулинга, двусторонний
LSTM(256), линейный слой в 63 класса, CTC-лосс — 4 623 615 параметров. PP-OCRv6: LCNetV4-бэкбон,
`hidden_size 192`, голова `Linear(192 → 18710)`, свой CTC-лосс (`torch.nn.CTCLoss(blank=0,
zero_infinity=True)`), потому что в `transformers` эта модель **не считает лосс сама**. Длина
временных шагов `T = W/8` (после `avg_pool2d(3,2)`) — её надо согласовать с `input_lengths`, иначе
CTC даёт «тихий» нулевой loss.

**5. Декод и маска.** CTC-декод: `argmax` по каждому шагу → схлопывание повторов → удаление blank.
**Маска по типу** — бесплатная точность: тип известен на инференсе, значит известен и алфавит
(`BotFilter` → только цифры, `CaptchaVerifyZ` → ровно 5 символов `0-9A-Z`), и запрещённые символы
можно просто замаскировать.

**6. Пост-обработка.** Шаг solver'а: развернуть (`reverse`), вычислить (`19 - 11`), слова→цифры
(лексикон на 40 строк). Дальше — ответ.

Полные разборы с реальными примерами, сравнение трёх моделей, карта скорости и список граблей —
в [`docs/INPUT_PIPELINE.md`](INPUT_PIPELINE.md).

«На 11.8 ГБ и 23 000 картинок» — что вообще можно запустить, а что нельзя.

## 7.1. Что реально влезает и имеет смысл

| Модель | Параметры | Инференс на 11.8 ГБ | Дообучение на 11.8 ГБ | Вердикт |
|---|---|---|---|---|
| `PP-OCRv6_medium_rec` | 19.1 М | ✅ | ✅ 2.34 ГБ @ batch 16, 101 img/s | **берём** |
| `PP-OCRv6_small_rec` | 5.3 М | ✅ | ✅ 1.11 ГБ, 170 img/s | быстрый пилот / «лёгкая» публикация |
| `PP-OCRv6_tiny_rec` | 1.1 М | ✅ | ✅ 0.35 ГБ, 325 img/s | для абляций; словарь 6906 — кириллицы там может не быть |

| `cyrillic_PP-OCRv5_mobile_rec` | ≈10 М | ✅ | ✅ (ONNX-веса, нужен конверт/порт) | вариант для кириллицы |

| Модель | Параметры | Проблема |
|---|---|---|
| `PaddleOCR-VL-1.6` | 959 М | инференс возможен, **дообучение в 11.8 ГБ не влезает** (AdamW + градиенты + активации) |
| `MinerU2.5` | 1.2 Б | то же + генеративное декодирование |
| `DeepSeek-OCR` / `dots.mocr` / `Qwen3-VL-4B` | 3–4 Б | не влезают при обучении; в inference — медленно |
| `olmOCR-2-7B`, `Chandra OCR 2` | 5.3–8.3 Б | то же; HF-карточки отдают 401 (приватные/gated) — **не проверено** |
| `TrOCR-base` | 333 М | 384×384, оценка 14–18 ГБ @ batch 16; наш харнесс не прогнал |
| диффузионные OCR (DODO, MinerU-Diffusion) | н/д | сложность + цена без выигрыша на коротком выводе |
| Liquid / LTC / CFC | сотни тыс. | готовых OCR-весов нет; задача не наша |

## 7.4. Четыре «правды о маркетинге», которые стоит запомнить

1. **«Победил миллиард параметров» — неправда.** `PP-OCRv5` — это 5 М параметров, и в своей статье
   прямо заявляет, что конкурирует с миллиардными VLM на OCR-бенчмарках
   ([arXiv:2603.24373](https://arxiv.org/abs/2603.24373)); `PP-OCRv6` повторяет это в диапазоне
   1.5–34.5 М ([arXiv:2606.13108](https://arxiv.org/abs/2606.13108)). Размер — не главное;
   главное — **домен и данные**.
2. **«Новая архитектура 2026 года» ≠ лучше на нашей задаче — и это измерено, а не мнение.**
   Новейшие VLM-ы 2025–2026 годов (PaddleOCR-VL-1.6, MinerU2.5, dots.ocr, DeepSeek-OCR) умеют
   разбирать страницы с таблицами и формулами — и именно поэтому они **не** про наши пять символов
   в чате. А «классика» `trocr-small-printed` на **наших** данных даёт **0.20 %** медианы против
   58.80 % у PP-OCRv6 — при том, что TrOCR считается «эталоном готовой OCR-модели»
   ([arXiv:2109.10282](https://arxiv.org/abs/2109.10282)).
3. **Разница между «хорошей» и «плохой» моделью у нас меньше, чем разница между «режем по полосе»
   и «режем по кадру».** Одна и та же `PP-OCRv6_medium_rec`: **0.5517** по полосе и **0.0345** по кадру
   на одних и тех же 29 типах — **в 16 раз**. Пока мы это не починим, любая смена модели упирается в
   тот же потолок.
4. **«Дообученная модель лучше исходной» — тоже неправда, и это тоже измерено.** Голый fine-tune
   PP-OCRv6 **ухудшил** held-out (58.80 % → 48.00 %). Выиграла не «больше обучения», а
   **интерполяция весов** (WiSE-FT): 63.80 %. Урок: **рецепт дообучения важнее самого факта
   дообучения**, и проверять надо на удержанных типах, а не на обучающих.

   дообучения. Их размеры/скорости в таблице — из их статей и карточек, а не из наших замеров.
2. **Liquid/LTC/CFC**: готовых OCR-весов не найдено; сравнительного замера «LTC vs CRNN на наших
   типах» не было. Публикаций с метриками на captcha-подобных данных не нашлось.
3. **Параметры** SATRN, PARSeq, SVTR/v2, ViTSTR, MGP-STR, PP-OCRv3/v4, Qwen-VL, DODO, MinerU-Diffusion —
   **не пересчитывались**: взяты из статей или из оценок. Пересчитаны только те, что есть в
   `reports/research3/MODEL_LANDSCAPE.md` §6.3 (PP-OCRv6 medium/small/tiny).
4. **Скорость и VRAM** для TrOCR, GOT-OCR2, PaddleOCR-VL, Qwen-VL, PARSeq — **оценки**, а не замеры
   (взять из той же таблицы `MODEL_LANDSCAPE.md`, где это честно помечено «оценка»).

   все цифры в §2.2.1 — с прошлого рендера (100 PNG на тип). Свежие цифры в §2.2.2 — из прогонов
   обучения, они измеряют **7 удержанных типов**, а не все 46.
