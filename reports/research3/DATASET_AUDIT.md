## 4. Баг 1 (измерен): `Archy-X/Krypton/map` — полоса ýже текста

**Код:** `dataset/generator/dev/captcha/gens/Krypton.java`
* `band()` — строки 123–134: ширина полосы = `sum(advance(глиф))`, **разделители не учтены**;
* `drawMapText()` — строки 493–518: `pen += w + 1` — между глифами остаётся **1 пустой столбец**;
* `advance()` — строки 477–487: «один за последним установленным пикселем» (обрезает глиф по ink).

**Измерение по пикселям (все 100 сэмплов, PNG = белой бумага + чёрный ink):**

```
сколько сэмплов, где ink выходит за правый край полосы: 100 из 100
распределение (ink_x1 - (roi_x+roi_w-1)) в px: {4: 100}      <- всегда ровно 4 px
ink-пикселей вне полосы: мин 4, медиана 11, макс 14
```

Три сэмпла с прогоном ink-колонок (= глифы) и рамкой полосы:

```
001.png  answer/text='6aFij'  roi=[27,32,21,8]  -> полоса покрывает x 27..47
   ink-колонки: 27–31, 33–37, 39–43, 45–45, 47–51     <- 5 глифов
   ink до x=51; за правым краем полосы (x>=47) -- 4 px
002.png  answer/text='C7s9V'  roi=[49,16,25,8]  -> полоса x 49..73
   ink-колонки: 49–53, 55–59, 61–65, 67–71, 73–77
003.png  answer/text='Ak916'  roi=[8,25,24,8]    -> полоса x 8..31
   ink-колонки: 8–12, 14–17, 19–23, 25–29, 31–35
```

ASCII-арт полосы `001.png` (символы с x=25; `|`-подобный сдвиг = 4 px за полосой):

```
....##........#####.#.....#....
...#..........#................
..#......###..###...#.....#....
..####......#.#.....#.....#....
..#...#..####.#.....#.....#....
..#...#.#...#.#.....#.#...#....
...###...####.#.....#.#...#....
```

**Вывод (измерен):** полоса обрезает **последний глиф целиком** во всех **100 из 100** сэмплах;
ширина текста = ширина полосы + (len−1) = +4 px для 5-символьного кода.
Метка `6aFij` в полосе физически не помещается → **нефитимая метка**, CTC-цель не подгоняется.
Починка (не в моих файлах): в `band()` прибавить `code.length() - 1` к ширине, затем пересобрать датасет.

## 5. Баг 2 (измерен): `LagBug/XProtect/reverse` — в `text` перевёрнутая строка

**Код:** `dataset/generator/dev/captcha/gens/XProtect.java:318-373` (класс `Reverse`)
* `answer()` (строки 340–342) возвращает `new StringBuilder(code).reverse().toString()`;
* на картинке рисуется **`code`** (строки 325–326), то есть **прямая** строка;
* `text()` **не переопределён** → `Cg.text()` по умолчанию возвращает `answer()` (то есть разворот).

**Три независимых доказательства из данных (100/100 сэмплов):**

1. **Из `prompt`:** в challenge-строке лежит нарисованный код — `prompt` = «XProtect » Please reverse the letters of the following code: **pZrkhS**.»; regex находит его в **100 из 100** сэмплов.
2. **Из меток:** `text == reverse(код из prompt)` — **100 из 100**; `text == answer` — **100 из 100**. То есть метка = разворот нарисованного.
3. **По пикселям:** полоса (48×20, моноширинный чат-шрифт `Monospaced` — `McUi.java:133`) разбита на 6 ячеек; шаблоны глифов собраны из самих сэмплов (116 различных растров, глиф ↔ символ — голосованием по коду из `prompt`), после чего полоса **декодирована**:

```
сэмплов декодировано:                    100
декодированная строка == text (метка):     0     <- в кадре НЕТ такой строки
декодированная строка == reverse(text):   100     <- в кадре ровно развёрнутая метка
```

**Вывод:** нарисованная строка = `reverse(text)`. Обучать распознаватель на `text` бессмысленно — он будет
учиться читать строку, которой в картинке нет. Починка (не в моих файлах): переопределить `text()`
в `Reverse` так, чтобы он возвращал нарисованный код, и пересобрать датасет.

### 5.1 Что изменится после починки (по уже сделанному в рабочем дереве diff)

Пока я писал отчёт, в `git status` появились правки именно этих двух файлов (их внёс **другой** агент;
мой бриф запрещает трогать `dataset/generator/**`):

```diff
Krypton.java (band(), ~строка 123)
+            w += Math.max(0, drawn - 1);   // ширина полосы += code.length()-1 = +4 px

XProtect.java (класс Reverse, ~строка 344)
+        @Override
+        public String text() {
+            return code;                   // нарисованный код, а не разворот
+        }
```

Обе правки **совпадают с моими измерениями** (§4: ровно +4 px; §5: нарисованная строка = `code`).
Следствия для плана (после пересборки датасета):

* `Archy-X/Krypton/map` становится **полностью годным** типом (полоса накрывает все 5 глифов);
* `LagBug/XProtect/reverse` становится **нормальным типом группы B**: `text` = нарисованный код,
  `answer` = `reverse(text)` → число типов с `text != answer` растёт с **8 до 9**, и reverse
  перестаёт быть «сломанной меткой» — его можно учить (распознаватель читает код, разворот делает solver);
* список «обязательно исключить» (§8) сокращается с **17 типов / 1700 картинок** до
  **15 типов / 1500 картинок**; `Krypton/map` и `reverse` переходят в обучение;
* все остальные числа отчёта (4600 / 46 / 29 типов с полосой / 1240 референсов) **не меняются**.

## 6. Статистика пригодности под обучение (три политики)

Политика (b) построена **из данных**: тип без полосы считается «ответ = весь кадр», если его `text`
совпадает с шаблоном кода `[0-9A-Za-z]{3,8}` и уникальных ответов > 20 (то есть это не константа
и не «название цвета»). Таких типов **8**: `InstantlyMoist/Captcha/textcaptcha`,
`LagBug/XProtect/code`, `LagBug/XProtect/map`, `irootdev/AnBot/captcha`,
`jonesdevelopment/sonar/{standard,legacy,complex}`, `BotFilter/map`.
Пограничный случай — `LagBug/XProtect/picture`: 20 уникальных ответов, алфавит `a-z`, полосы нет,
весь кадр = текст, но порог `>20` его не взял; при пороге `≥20` политика (b) становится
**38 типов / 3800 картинок**, а (c) — **30 / 3000**.

| Политика | Типов | Картинок | из них latin-charset |
|---|---|---|---|
| **(a)** только типы с полосой `roi` | 29 | **2900** | 16 типов / 1600 |
| **(b)** + типы без полосы, где ответ = весь кадр | 37 | **3700** | 24 типов / 2400 |
| **(c)** (b) минус константные ответы и нечитаемые | 29 | **2900** | 19 типов / 1900 |
| **(c′)** (c) минус 2 типа с дефектами генераторов (`reverse`, `Krypton/map`) | 27 | **2700** | 17 типов / 1700 |

Группы A+B (по HANDOVER) = 31 тип / 3100 картинок, **но с полосой только 21 тип / 2100 картинок**.

**Главное ограничение, о котором надо знать до запуска** (`train/train.py:223-229`): тип отбрасывается,
если **хоть одна** строка содержит символ вне charset. `CHARSET` = 62 латинских символа **без пробела**,
`CYRILLIC` = 33 буквы, тоже **без пробела**. Поэтому из 29 «годных» типов **10** содержат
несовместимые метки:

```
GalleryCaptcha/ru-symbols          вне charset: ЁАБВГДЕЖЗИЙКЛМНОПРСТУФХЦЧШЩЪЫЬЭЮЯ
LimboFilter/symbols          вне charset: ЁАБВГДЕЖЗИЙКЛМНОПРСТУФХЦЧШЩЪЫЬЭЮЯ
GalleryCaptcha/ru-numberword       вне charset: <пробел> + кириллица
GalleryCaptcha/ru-numberword-caption  вне charset: <пробел> + кириллица
LimboFilter/map              вне charset: <пробел> + кириллица
LagBug/XProtect/equation     вне charset: <пробел> + -
FeelingAlive0/AdvancedCaptcha/math  вне charset: <пробел> + * + -
Mrbysco/Captcha/math         вне charset: <пробел> + +
LagBug/XProtect/gui          вне charset: <пробел> + '
Yukun99/Captchas/itemslot     вне charset: <пробел> + '
```

**Итог: при `--charset latin` в Model A реально доезжают 19 типов / 1900 картинок** из 46 типов / 4600.
Это не «модель плохая», это фильтр в тренайере: пока в charset нет пробела, 10 типов молча выпадают.

## 7. План сплита (3 варианта, по убыванию строгости)

**Правило, общее для всех трёх вариантов:** удерживаем **целый плагин/семейство**, а не отдельный тип.
Один тип из семейства в train и второй из того же семейства в val = утечка (тот же шрифт, тот же
рендерер, та же палитра), и метрика обобщения становится бессмысленной.

**Оценка времени (это оценка, не измерение).** Скорость GPU `920 img/s` (`HANDOVER.md` §1.0);
измеренный end-to-end прогон (`reports/TRAINING_MINIMAL_LATIN.md`: 1000 картинок × 300 эпох = 12.4 мин)
даёт **403 img/s** с учётом декодирования картинок. Ниже — оба числа; планировать надо по худшему.
Модель — CRNN+CTC, 4 623 615 параметров, batch 32, 300 эпох.

⚠️ **Две ловушки этого варианта:**
1. **10 из 22 типов обучения — charset-poison** (§6). При `--charset latin` тренайер их отбросит,

### Вариант 3 — расширенный: + кириллица (отдельная модель B)

**Добавляются 5 типов / 500 картинок:** `GalleryCaptcha/ru-numberword`, `GalleryCaptcha/ru-numberword-caption`,
`LimboFilter/map`, `GalleryCaptcha/ru-symbols`, `LimboFilter/symbols` (кириллица; 3 из них — с пробелом).

**Что это даёт:** 3 типа с русскими словами-числами (картинка → слова → цифры) — это отдельный
домен: латинская модель их не прочитает в принципе, а 500 картинок кириллицы — это +26 % к
реально доступным данным модели B.

**Какая цена:**
1. **Нужен отдельный charset.** `CYRILLIC` = 33 буквы (`train/captcha_crnn.py`), а в метках
   `LimboFilter/symbols` и `GalleryCaptcha/ru-symbols` есть цифры → они **молча выпадают** из CTC-цели
   (это уже зафиксировано в `train/AGENTS.md`). Лечится расширением до 44 классов.
2. **Нужен отдельный прогон** (Model B): смешивать 62 латинских + 33 кириллических + 10 цифр в один
   softmax хуже, чем два головы; при 500 картинках кириллицы один прогон на 96 классов
   гарантированно переобучится.
3. **Пробел в метках.** У всех трёх «числовых слов» метка содержит пробел — без пробела в charset
   типы отбрасываются как poison (и в кириллическом режиме: `CYRILLIC` пробела не содержит).
4. `LimboFilter/{map,framed2x2,framed3x3}` — двух-трёхстрочный блок: глиф ≈ 1/5 полосы,
   строки слипаются (это уже в `EXCLUDE` тренайера — правильно).

**Оценка времени:** латиница 2200 + кириллица 500 = **≈14.7 мин** @920 img/s (≈33 мин @403).

## 8. Рекомендация

1. **Сначала починить два бага генераторов** (`Krypton.band()` — `+code.length()-1`;
   `Reverse.text()` — возвращать нарисованный код) и **пересобрать датасет** (~1 мин).
   Без этого окно обучения тратится на два типа с заведомо нефитимыми метками, а «датасет — артефакт»,
   значит учить надо на пересобранной папке. Это делает оркестратор (мой бриф не даёт права трогать
   `dataset/generator/**`). **Правки в оба файла уже в рабочем дереве** (§5.1) — остаётся пересборка.
2. **Параллельно починить charset в тренайере** (`train/` — чужой файл): добавить пробел (и `+-*'`)
   в `CHARSET`, расширить `CYRILLIC` до 44 классов. Без этого 10 из 29 «годных» типов молча
   выпадают, и обучение идёт на 12 типах вместо 22.
3. **В окно 1–2 часа запускать Вариант 1** (удержать 7 типов из 5 плагинов: sonar×3, BotFilter,
   CaptchaVerifyZ, laforetbrut, JSH32; обучить остальные 22 типа / 2200 картинок).
   Он даёт честное измерение обобщения на невиданные плагины/шрифты/цвета и укладывается
   в окно с запасом: **≈12 мин чистого GPU, ≈27 мин по измеренной скорости** на 300 эпох,
   плюс оценка per-type. Главная метрика — **exact match и CER по типам + медиана по типам**,
   не среднее по фолду.
4. **Если останется время** (окно 2 ч) — досчитать Вариант 2 (4 фолда по семействам):
   ещё ≈47 мин (≈108 мин по реальной скорости). Порядок запуска: сначала Вариант 1 (он даёт
   ответ «учится или запоминает»), потом уже 4-фолд.
5. **Вариант 3 (кириллица) — не в это окно.** Он требует правки charset и отдельного прогона;
   это работа на следующую сессию.

**Обязательно исключить из обучения (17 типов, 1700 картинок):**
`LagBug/XProtect/{drop,jump,sneak,different}` (константный ответ), `China2B2T/Captcha/wool`

(номер слота; 7 уникальных картинок на 100), `jSdCool/minecaptcha/image` (63–70 символов,

**Условно исключить (до починки полосы/метки):** `Archy-X/Krypton/map`.
